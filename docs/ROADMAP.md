Percentages represent verified implementation scope, not launch readiness. A phase is complete only after its acceptance checks pass. See [Implementation status and release blockers](IMPLEMENTATION_STATUS.md) for the current evidence-based matrix.

## Current implementation update — 2026-11-26

- Account deletion now requires current-password reauthentication in addition to the existing CSRF/origin checks and explicit browser confirmation. The endpoint applies a user-scoped rate limit before validating the password and does not begin the destructive workspace/account transaction on an incorrect password. The dashboard collects the password and sends it only in the authenticated deletion request. Source-only; no live deletion or browser acceptance was run.

- PostgreSQL backups now run `pg_restore --list` against the temporary archive before publishing the final dump and checksum, so an unreadable archive is not promoted as a completed backup. Restore also performs a read-only inspection of the destination database before invoking `pg_restore`. It rejects targets containing user schemas, relations, routines or custom types, in addition to requiring a different source/target identity and explicit confirmation. This closes the gap where a non-empty target could be passed to a restore command despite the documented empty-target requirement. No database restore was run.

- The API `/ready` gate now requires migrations 063–069 and the billing price-history, daily research quota, editorial article/CMS, project-scoped WordPress and saved-research schema. Previously it checked only through migration 062 and could return ready with newer feature tables absent. The readiness query now verifies the 69-migration ledger count and the added critical tables/columns. Source-only; no live database query or migration was run.

- Database readiness and release preflight now track the full migration series through 069_workspace_research_history.sql, including platform billing price-history, daily research quota, editorial briefs/articles, project-scoped WordPress connections and saved research-history schema. The read-only schema diagnostic now checks the associated tables, key columns and indexes, so a database missing these newer feature migrations cannot be reported ready. This is source-only; no live database was queried or migrated.
- Current application implementation source on main: `1b9b62da7f5165025c167f581126900fac7b3761`. This is a source-control reference, not a CI or deployment claim.


- Added a platform-admin-only WhatsApp webhook recovery workflow: a payload-free, paginated dead-letter queue in the admin dashboard plus an explicit per-event requeue confirmation. Replay is available only when the event's phone asset is currently mapped to an active WhatsApp account; the backend atomically requeues only an eligible unprocessed dead-letter event and records an audit event with the exact previous attempt count. Inactive/unmapped phone assets are visibly blocked from replay. This does not expose payloads or enable outbound sending. Source-only; no database/runtime or Meta provider acceptance was run.

- WhatsApp webhook operations now expose a platform-admin-only, read-only dead-letter view with bounded pagination and aggregate counts. It returns event metadata and retry/error timestamps only; raw webhook payloads and message content are never exposed. Source-only; no database/runtime acceptance or Meta provider acceptance was run.
- Analytics now counts WhatsApp provider-confirmed delivery cumulatively: a `read` status also qualifies as delivered, so later read transitions no longer make delivered totals fall. Workspace summary exposes distinct provider-confirmed deliveries and reads; campaign metrics derive these from persisted provider status events in the selected reporting window rather than only the delivery row's current state. Source-only; SQL/runtime and dashboard acceptance remain pending.
- Saved research history now paginates in 30-record batches with server-side `has_more`/`next_offset` metadata. The dashboard loads older runs on demand, deduplicates appended records, resets to the newest page after a successful search, and adjusts the next offset after a manual deletion. Source-only; no browser/database acceptance has been run.
- WhatsApp integration status copy now distinguishes the application dispatch gate from actual Meta sandbox/production acceptance, avoiding the implication that a configured flag proves provider readiness. No live sending or provider acceptance was performed.
- Research-history storage is bounded to the newest 500 successful runs per workspace. New snapshots and pruning occur in one database transaction, serialized by locking the workspace row so concurrent searches cannot race the cap; older snapshots are removed automatically, while manual per-run deletion remains available. Source-only; migration/runtime behavior has not been tested.
- Prospect research provider resilience: Brave remains preferred, but a valid empty Brave result set now triggers the configured SerpAPI fallback. If fallback is unavailable, a genuine empty Brave response is preserved as a successful empty result rather than misreported as provider outage. Source-only; no provider credentials or live searches were exercised.
- WhatsApp dispatch gate consistency: the scheduler endpoint, queue API diagnostics and workspace integration-status response now all use the same `dispatch_is_enabled()` helper, which requires both the parsed application setting and exact `WHATSAPP_DISPATCH_ENABLED=true` environment opt-in. This avoids reporting dispatch enabled when the worker's second gate would reject it. Source-only; no tests or live sends.
- WhatsApp outbound queue pagination: the authenticated queue endpoint now returns `has_more` and `next_offset` using one-row lookahead, and the dashboard can incrementally load additional workspace records without duplicates. Queue cancellation remains limited to queued items and releases the associated reserved quota. Source-only; no tests/build/browser acceptance were run.
- The dashboard now lists the latest 50 workspace WhatsApp outbound queue records with account/prospect, status, attempts and timestamps. Workspace owners/admins can cancel a still-queued item; cancellation releases its unused quota reservation. The UI clearly distinguishes queued intent from confirmed delivery. This is source-only and has not been browser-tested.

Public publishing also locks its pinned connection while claiming the publish operation, serializing concurrent disconnect and credential changes against both delivery paths. A concurrent site/credential update cannot switch the destination between connection selection and the first delivery attempt; site URL changes are blocked after any article is pinned, including ambiguous attempts without a saved post ID.

Article delivery buttons no longer depend on whichever connection scope happens to be selected in settings: the backend resolves the correct connection from each saved article's project and enforces fail-closed behavior. Concurrent connection setup for the same scope is serialized. An unpinned project-specific override can be removed to restore workspace fallback; if articles are already pinned to it, disconnect retains a disabled record and keeps delivery fail-closed.

## Release rules

1. Work on `main` only; no extra branches.
2. Keep real credentials in encrypted environment/secret storage; never commit or log them.
3. Keep external sending, real payments, and website writes gated until staging acceptance and explicit release approval.
4. CI success verifies only the tested commit and checks; it does not prove production readiness or external provider operation.
